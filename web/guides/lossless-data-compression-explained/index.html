How Lossless Data Compression Algorithms Work: Huffman, RLE, and LZ77

By Shahrukh Ummati (Summati) • November 08, 2026 • 12 min read (1,450 words) • Algorithmic Computer Science

In computer systems and distributed networking, every byte transmitted over a network wire or written to solid-state storage carries tangible monetary and latency costs. Lossless data compression is the mathematical process of reducing the physical size of a digital payload while guaranteeing that the decompressed output is bit-for-bit identical to the original input.

Unlike lossy compression (commonly used in JPEG photography or MP3 audio where minor perceptual fidelity is sacrificed for drastic size savings), lossless compression cannot afford to drop a single bit. If an executable binary or an SQL database backup loses even one byte, the entire file corrupts. In this guide, we break down the core mathematical theory of information entropy and analyze the three most influential lossless algorithms that power modern engines like Karakorum, Gzip, and Deflate.

1. The Theoretical Limit: Shannon Entropy

Before examining specific algorithms, we must understand the fundamental theoretical barrier of data compression: Shannon Entropy, formulated by Claude Shannon in 1948. Entropy measures the average amount of information produced by a stochastic source of data.

Mathematically, Shannon entropy \( H(X) \) is defined as:

H(X) = - Σ [ P(x_i) * log2(P(x_i)) ]

Where \( P(x_i) \) is the probability of occurrence of character \( x_i \). If every byte in a 256-byte character set appears with equal probability (pure uniform random noise), the entropy is 8 bits per byte, meaning the data cannot be compressed losslessly by any algorithm. However, human language, computer code, JSON structures, and system logs are wildly redundant. Certain symbols (like vowels in text or curly braces in JSON) appear far more frequently than others. This statistical redundancy is what allows compression algorithms to reduce file sizes.

2. Run-Length Encoding (RLE)

Run-Length Encoding (RLE) is one of the simplest forms of lossless compression. It operates on sequences where the same data value occurs in many consecutive data elements (called "runs").

How RLE Works

Instead of storing repetitive sequences literally, RLE replaces consecutive duplicate bytes with a count byte followed by the value byte.

Uncompressed Stream: AAAAAAAAAABBBCCCCDDDDDDDDDD (27 bytes)
RLE Encoded Stream:  10A3B4C10D (8 bytes)
Compression Ratio:   27 / 8 = 3.37x

While RLE is exceptionally fast with near-zero CPU overhead, it performs poorly on complex textual data where duplicate characters rarely appear consecutively. In fact, if applied to non-repetitive text (e.g. ABCDEF), naive RLE can actually expand the file size to twice its original volume. Consequently, modern engines use adaptive RLE strictly as a pre-filtering pass for bitmap masks, sparse vectors, or binary memory dumps.

3. Huffman Coding: Frequency-Based Variable Length Prefixes

Published by David Huffman in 1952, Huffman Coding is an entropy-encoding algorithm that assigns variable-length codes to input characters based on their statistical frequencies. The most frequent characters get the shortest bit codes, while rarer characters receive longer bit sequences.

The Prefix Property

In standard ASCII or UTF-8, every character consumes fixed 8-bit blocks (e.g. e is 01100101). If we assign a 2-bit code to e and a 12-bit code to z, how does the decompressor know where one character ends and the next begins? This is resolved by the Prefix Property: no code assigned to any character can be a prefix of another character's code.

Building a Huffman Tree

  1. Count the frequency of each unique byte in the source payload.
  2. Place all unique bytes into a priority queue (min-heap) ordered by frequency.
  3. Continuously pop the two lowest-frequency nodes, create a parent node whose frequency is the sum of both children, and push the parent back into the queue.
  4. Repeat until only a single root node remains. This forms the binary Huffman Tree.
  5. Assign 0 to all left branches and 1 to all right branches. The path from the root to each leaf node defines that character's exact bit representation.
Character Standard ASCII Bits Calculated Frequency Huffman Variable Bitcode
' ' (Space) 8 bits 35% 0 (1 bit)
'e' 8 bits 25% 10 (2 bits)
't' 8 bits 15% 110 (3 bits)
'q' 8 bits 1% 111101 (6 bits)

4. The LZ77 Algorithm: Dictionary Sliding Windows

Developed by Abraham Lempel and Jacob Ziv in 1977, LZ77 replaced statistical frequency modeling with dynamic dictionary matching. Instead of looking at individual characters, LZ77 identifies repeated substrings across a sliding window of historical data.

The Sliding Window Mechanism

The LZ77 engine maintains two conceptual buffers as it processes a byte stream:

  • Search Buffer: A window of recently processed history (typically 32KB to 256KB in size).
  • Lookahead Buffer: The upcoming sequence of bytes waiting to be encoded.

When the algorithm scans the lookahead buffer, it searches backwards through the search buffer for the longest matching substring. If a match is found, it outputs a reference triplet:

(Distance backwards, Length of match, Next literal byte)
Example in Action:
Text: the cat sat on the mat
When encoding the second the, instead of writing the letters t-h-e, LZ77 outputs (offset: 15, length: 3), pointing back to the first instance. For large JSON APIs and source code where repetitive key names (e.g. "created_at", "user_id") appear thousands of times, LZ77 routinely achieves 70% to 85% compression ratios.

5. How Modern Engines Combine Them (Deflate & Karakorum)

Modern high-performance engines do not rely on just one algorithm in isolation. The industry-standard Deflate algorithm (and the engine powering Karakorum) utilizes a multi-stage pipeline:

  1. Stage 1 (Sliding Window): The raw byte stream is first processed by LZ77, transforming repeated phrases into distance-length tokens.
  2. Stage 2 (Huffman Encoding): The resulting literal bytes and distance/length values are compressed a second time using dynamic Huffman coding trees.
  3. Stage 3 (Integrity Verification): A cryptographic checksum (SHA-256 or Adler-32) is appended to guarantee zero data loss.

Conclusion

Lossless data compression remains one of the cornerstones of modern computer science. By combining the phrase-matching power of LZ77 with the mathematical optimality of Huffman prefix trees, modern engines can ingest massive datasets and stream them over networks at fractions of their original size.
